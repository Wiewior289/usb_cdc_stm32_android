# CZAR V1 - Android reference

This document records the frozen wire contract implemented by the Android probe. It is not a replacement for the shared specification agreed by the Android and STM32 sides.

## Common fields

- MAGIC: bytes `43 5A 41 52` (ASCII `CZAR`).
- VERSION: `0x01`.
- TYPE_REQUEST: `0x01`.
- TYPE_RESPONSE: `0x02`.
- Every multi-byte integer is little-endian.
- Maximum valid request/response payload: 2048 bytes.
- Request payload length 1..2048. A zero-length request is reserved for the LENGTH_ERROR diagnostic case and is not generated by this Android application.
- CRC: CRC-32/ISO-HDLC (reflected polynomial `0xEDB88320`, init `0xFFFFFFFF`, RefIn/RefOut true, XorOut `0xFFFFFFFF`), stored as an unsigned 32-bit little-endian value.

## Request layout

| Field | Size | Offset |
|---|---:|---:|
| MAGIC | 4 | 0 |
| VERSION | 1 | 4 |
| TYPE | 1 | 5 |
| SESSION_ID | 4 | 6 |
| SEQUENCE | 4 | 10 |
| PAYLOAD_LEN | 2 | 14 |
| ANDROID_TX_NS | 8 | 16 |
| PAYLOAD | N | 24 |
| CRC32 | 4 | 24 + N |

Request total length: `28 + N`, maximum 2076 bytes.

## Response layout

| Field | Size | Offset |
|---|---:|---:|
| MAGIC | 4 | 0 |
| VERSION | 1 | 4 |
| TYPE | 1 | 5 |
| SESSION_ID | 4 | 6 |
| SEQUENCE | 4 | 10 |
| PAYLOAD_LEN | 2 | 14 |
| STM32_RX_US | 4 | 16 |
| STM32_TX_US | 4 | 20 |
| STATUS | 1 | 24 |
| PAYLOAD | N | 25 |
| CRC32 | 4 | 25 + N |

Response total length: `29 + N`, maximum 2077 bytes.

For both directions, CRC covers VERSION through the last PAYLOAD byte. It excludes MAGIC and the four-byte CRC field itself.

## CRC reference vector

The ASCII bytes `31 32 33 34 35 36 37 38 39` (`123456789`) produce CRC-32/ISO-HDLC:

- Numeric value: `0xCBF43926`
- Wire bytes, little-endian: `26 39 F4 CB`

Both implementations should retain this as a common first-level test vector.

## Shared frame vectors

The following fixed values are used by both Android and STM32 tests:

- SESSION_ID: `0x78563412`
- SEQUENCE: `0x0C0B0A09`
- PAYLOAD_LEN: `2`
- ANDROID_TX_NS: `0x0807060504030201`
- Payload: `29 3A` (matches the modulo-256 payload formula)
- Response STM32_RX_US: `0x11223344`
- Response STM32_TX_US: `0x11223399`
- Response STATUS: `0x00`

Request frame, including CRC:

```
43 5A 41 52 01 01 12 34 56 78 09 0A 0B 0C
02 00 01 02 03 04 05 06 07 08 29 3A B9 9E B1 38
```

Response frame, including CRC:

```
43 5A 41 52 01 02 12 34 56 78 09 0A 0B 0C
02 00 44 33 22 11 99 33 22 11 00 29 3A 07 DA 90 10
```

These frame vectors verify offsets, endian handling and CRC coverage in addition to the standalone CRC check vector.

## Session, sequence and payload

- Android generates a random 32-bit SESSION_ID for the app session.
- SEQUENCE begins at zero and increments modulo 2^32 for each request.
- Android sends one request and waits for its matching response before sending the next request (stop-and-wait).
- Expected payload byte:

`P[i] = (SESSION_ID + 31 * SEQUENCE + 17 * i) mod 256`

The STM32 response with STATUS=OK echoes the request payload byte-for-byte.

## STATUS

| Value | Name | Android interpretation |
|---:|---|---|
| `0x00` | OK | Requires the expected payload length and exact payload echo |
| `0x01` | LENGTH_ERROR | Valid protocol diagnostic response |
| `0x02` | PAYLOAD_ERROR | Valid protocol diagnostic response |
| `0x03` | UNSUPPORTED_TYPE | Valid protocol diagnostic response |
| `0x04` | CRC_ERROR | Valid protocol diagnostic response; PAYLOAD_LEN must be zero |

Every accepted response must itself have valid MAGIC, declared bounded length and CRC, and must match the outstanding SESSION_ID and SEQUENCE. A CRC_ERROR response is diagnostic only: because the original request header might also have been corrupted, matching identifiers are still checked rather than trusted.

## Timestamp semantics

- ANDROID_TX_NS is captured with `System.nanoTime()` immediately before the request is sent.
- STM32_RX_US is captured after the complete request frame has been received.
- STM32_TX_US is captured immediately before submitting the response to the CDC transmit path.
- Android RX time is captured when the USB bulk-IN read containing the completed response returns.
- RTT is Android RX minus ANDROID_TX_NS.
- STM32 processing time is the unsigned modulo-2^32 difference `STM32_TX_US - STM32_RX_US`. This is valid when the measured interval is shorter than one full 32-bit TIM2 period.

RTT minus STM32 processing is not a pure USB wire-time measurement. It includes Android scheduling, USB stack and device-side transport effects.

## Stream handling

A USB bulkTransfer result is an arbitrary byte-stream fragment, not an application-frame boundary. The decoder supports fragmented and concatenated frames. A valid frame is consumed using its declared bounded length, so MAGIC bytes inside a valid payload do not split it. A malformed candidate is discarded incrementally while searching for the next MAGIC candidate; CRC is required before a frame is accepted.
